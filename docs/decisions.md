# Decisions

- D-1 (owner, 2026-11-03) Devices with special features (appliances, vacuums, intercoms, remotes) are brand independent: the user chooses the entities with an entity selector; the dashboard looks at the entity's domain, device class, unit, options and supported features. Nothing is hidden behind a brand name. A section with nothing bound or supported is not shown (a vacuum without a map has no map section; a custom picture can be given instead).
- D-2 (owner) A good-looking default layout for each such device that works with whatever is bound, using the dashboard's existing rows and components.
- D-3 (owner) When Hue Plus and scene engine are both installed, Hue lights are played by Hue Plus; scene engine plays every other light. A scene with both is played coherently on one clock. Scene engine holds nothing Hue-specific: it gets Hue's abilities from Hue Plus, like an expansion pack.
- D-4 (owner) Existing Hue Plus scenes that contain non-Hue lights keep working; new or edited mixed scenes belong to scene engine. Nothing is migrated automatically.
- D-5 (owner) Scene engine is updated for Home Assistant 2026.10 and published as a public repository next to the others.
- D-6 (owner) A device without an area in Home Assistant is placed by the user in a room; the choice is stored with the dashboard layout and Home Assistant's areas are not changed.
- D-7 (owner) The remote creator is a kind in the "Add device" list. The remote shows as a normal row and opens a popup with a grid of buttons. The grid has 3 columns by default; the number of columns is adjustable per remote and a button can take 2 columns. Each button has an entity and an icon (and an optional label).
- D-8 (owner) An image remote takes a picture by upload or by an existing `/local/` path. Touch areas are drawn over the picture. Nothing says "command sent": a message appears only when a command fails.
- D-9 (owner) A notification rule can watch any entity reaching a state; the battery rule also takes binary low-battery sensors.
- D-10 (owner) Push to talk is wanted for the intercom and for cameras that have a speaker (the guest room camera).
- D-11 (owner) Releases of home-control, hue-plus and scene-engine are published by the assistant when CI passes.
- D-12 (owner, 2026-11-07) Home Control is a scene engine for any light, and it is brand independent. Live scenes, areas, their storage, playing and the services that drive them live in Home Control's integration (the browser only shows and edits them), for every light. Supersedes D-3 and D-4 (Hue Plus no longer plays Hue lights, and scene engine is not a partner) and D-21 of Hue Plus ("Hue Plus owns live scenes, areas and effects"). Scene engine is removed when this is done: its repository is deleted on GitHub (owner's choice, 2026-11-07, after everything is verified; a git bundle of its history is kept in this folder).
- D-13 (owner, 2026-11-07) A "plus" integration (Hue Plus, a future Govee Plus) expands what Home Control can do for the lights of one brand. It is declared by a file `home_control.json` in its own folder and by services it provides: no Python import in either direction, so load order does not matter and a missing integration just disappears from the dashboard. The declaration names the lights it owns (by entity registry platform) and their command rate, the light effects it plays natively (id, label, group, icon), and a settings menu script (`menu.js`) that Home Control loads on the administrator's Settings page. Playing is a service of the plus integration. Without one, Home Control plays every light through `light.turn_on` and shows the effects the light and Home Assistant report. Decided in D-13: Hue Plus keeps everything that talks to the bridge itself (entertainment areas, Spotify sync, gradient zones, other bridge, Hue cloud, bridge scenes and their import, calibrated native effects and the bridge's command pacing). The Hue Plus menu in Settings and the effect catalogue move out of Home Control into Hue Plus (step B).
- D-14 (owner, 2026-11-07) Nothing the owner sees or does on the dashboard may change when this is done, with Hue Plus installed: same screens, same behaviour, same saved scenes and areas. Uninstalling a plus integration must not break scenes or areas: they keep working on the lights Home Assistant has left. So a saved area light keeps the light's entity registry `unique_id` next to its entity id, and an entity id that no longer exists is found again by that unique id (Hue Plus's entity and the Hue integration's own entity of a light share it).
- D-15 (owner, 2026-11-07) Light effects are data, not code in the dashboard. One catalogue syntax (`docs/effects-file.md`, JSON, schema 1) describes a brand's effects: their groups, labels, icons or preview colours, default brightness and speed, the calibration of the speed (which part of the light's own scale the slider covers) and colour variants. A plus integration ships its catalogue in `home_control.json` (Hue Plus: everything that was in the dashboard's Hue table) and a user can import a file in the same syntax, for any other brand, written by hand or with an AI's help; the dashboard validates it and says exactly what is wrong. A light's effects that no catalogue knows are listed as the light and Home Assistant report them. A file never carries code: the only picture it may carry is a palette or a named icon. A plus integration may also carry a picture (SVG) for an effect; it is checked against a short list of elements and attributes on both sides.
- D-16 (owner, 2026-11-07) A light that fades by itself is given its fade; one that cannot is given single commands at an update rate (1 to 60 per second, default 2, per scene) and this is marked experimental. A light the colour check let go of rejoins the scene when it shows the scene's colours again (a person's change is final: D-3).
- D-17 (owner, 2026-11-07) The Hue-specific parts of the dashboard are Hue Plus's, through the plugin API: Hue's scenes (rows, popup, light-panel tiles, import as a live scene), the Spotify sync and sync box, and the style choice of a gradient light. The dashboard keeps what is brand-independent: a *light made of zones* (the `zone_colors` and `entity_id` attributes) with its markers, its place in areas and live scenes, and a list for importing live scenes from any registered source. Without Hue Plus a scene of the Hue integration runs like any scene. The plugin API is only added to; a change to what exists increments `version`.
- D-18 (owner, 2026-11-07) In a live scene the zones of one strip (a light made of zones, found by the unique id of the light they are parts of) cover the palette between them in proportion to the scene's Range, whatever the strip's length, and stay centred on where the strip stands; the other lights are still placed by position. A look given to a strip is for the strip: an effect of its own that its plus integration can play makes the strip one light in the scene (its zones are not commanded), any other look goes to each zone. A light that was off when a scene started is not taken for one someone switched off until 10 seconds after its command was sent.
- D-19 (owner, 2026-11-07) In the live scene maker the colours come only from the Colors light, which the engine cycles and sends to the lights. The lights are not controlled from the maker except to include or leave out a light, give it its own brightness (the scene's brightness when no light is selected) and its own effect (with No effect first). No colour is shown for, or set on, a light, and colours are not joined to lights. A scene has a mode: linear (colours blend) or segmented (each colour as it is, no colour between). In both, a change is always a continuous smooth fade, a blend fading for twice the gap to the light's next command, a segment fading from its colour to the next across the whole segment, so it never rests; the other two Hue styles are not live scene modes. A gradient light's zones are played as separate lights next to each other (all five, which for a Hue light means its Segmented style while a scene plays, left as it is when the scene stops).
- D-20 (owner, 2026-11-10) A door call is for everyone in the household, not only administrators: when a camera's intercom rings, a popup with the camera, answer, end, unlock and talk opens by itself on every open dashboard (access rules of the camera apply), and a dashboard opened during a call opens it (the call's notification opens the dashboard). It is brand independent: the call indicator says whether it rings and publishes the paths of the audio (`docs/intercom-contract.md`). Talking must also work on a local http address: a browser gives no microphone there, so Talk uses the phone app's own Assist when there is one.
- D-21 (owner, 2026-11-16: "do all of them", after the trade-offs were put to them) The dashboard keeps on each device a copy of the registries and of the saved dashboard of the person's last visit (`home_control_registry_v1`, `home_control_layout_v1` in the browser's local storage, under the user id) and is first drawn from them while the real ones are asked for. The copies hold what Home Assistant already shows that person (entity ids and names, the saved layout), nothing else; a copy of another person, an old version, one more than 30 days old (registries) or one that cannot be read is not used; a browser that refuses storage just starts as before. The real data replaces the copy in place. Nothing is ever saved on top of the copy: a save waits until the real saved dashboard has been read, and a save that failed because the connection was down is made again when it is back. The registries' copy is not what the first layout is built from (that waits for Home Assistant's answer).
- D-22 (owner, 2026-11-19) A light group on the dashboard is a Home Assistant Group helper of the type light, made by the dashboard through the helper's configuration flow when the new light group form, opened from the lights checked under "Light group" in an add popup, is saved with a name (nothing is made before that: the name chooses the entity id; a rename later does not change it), and changed through its options flow when the group's settings are saved. The helper is deleted only from the group's settings after a confirmation (never by removing the group from a page). The group's lights are hidden in Home Assistant by default. Only administrators can do any of it. Assistant's choices within it: at least two lights; the helper is the single owner of the group's lights (the dashboard keeps no copy); name and icon are kept on the dashboard's device and the name is also written to the helper.
- D-23 (owner, 2026-11-24, after the trade-offs were put to them) Scenes are shared with Siri, HomeKit and the Shortcuts app from one page of the dashboard's Settings (*Siri and HomeKit*), for administrators only, a row per scene with two switches. (1) A live scene (kept by Home Control) is *published* as a Home Assistant `scene` entity that Home Control makes (unique id from the saved scene's id, name followed from the scene): activating it starts the live scene. Scenes that already are entities (classic, Hue, any `scene.*`) and the switches a plus integration registers as sync (Hue Plus's Spotify sync) are shared as they are, so nothing in Hue Plus changes. (2) *HomeKit* adds or removes the entity in the entity list of the HomeKit Bridge (Home Assistant's own integration) by changing that config entry's `filter` option the way the bridge's own form writes it, from Home Control's Python through an administrator-only websocket command; nothing else of the entry is touched and the bridge reloads itself. (3) *Shortcuts*: the Home Assistant app lists scene entities in the Shortcuts app by itself, so the dashboard creates nothing there; it shows the exact name to look for and a short how-to. Assistant's choices within it: only `scene`, `script` and `switch` entities can be exposed; the first bridge in bridge mode is the one changed (accessory-mode entries are left alone) and the page names it; a published scene is removed only by unpublishing it or deleting the scene, and switching HomeKit off never deletes it; the dashboard's own static scenes (device settings run from the browser) are not shared, because they have no server side to run.
- D-24 (owner, 2026-11-24: "a way to add a homekit bridge from dashboard which dashboard will use to add selected devices to homekit, supports TVs (the info button becomes the home button on the added device), air conditioner as heater cooler, fans, air purifiers and whatever else you can add. Single bridge, select what to add") The dashboard makes and manages one HomeKit Bridge and puts the chosen devices on it, in a new Settings page (*HomeKit*), for administrators only. (1) The bridge is made through Home Assistant's own HomeKit setup form, driven by Home Control's Python; it starts with a list that shows nothing (a bridge with an empty list shows every entity) and may carry TVs and locks, which Home Assistant would otherwise pair one by one. If a bridge exists (bridge mode, not set up in configuration.yaml) it is the one used, and no second is made. The page shows the code to enter, and the picture to scan, while it is not paired. (2) What is chosen is the dashboard's own devices (by entity), anything else HomeKit has an accessory for (picked by entity), and the scenes of the Siri and HomeKit page. An air conditioner is shown as a heater cooler, an air purifier as an air purifier, a fan as a fan, a TV as a TV, a speaker or receiver as what Home Assistant makes of it; the accessory type is the bridge's own per-entity `type` setting, and nothing else of the bridge's settings is changed. (3) Info on the Home app's remote is the TV's Home key: Home Assistant announces the key with an event and leaves it unhandled; Home Control listens and sends the one call the dashboard chose for that TV (the key its remote has for Home, `remote.send_command` or webOS `button`, nothing else), kept by Home Control so it works with the dashboard closed. Assistant's choices within it: the bridge is named by Home Assistant ("HASS Bridge"); a TV or lock added to the bridge sets the bridge to carry such accessories (Home Assistant warns that a TV of its own pairing performs better); taking the last entity off leaves a list that shows nothing, never one that shows everything; cameras and activity remotes are not offered; there is no limit check, Home Assistant keeps the first 150 accessories.
- D-25 (owner, 2026-11-25: "every section is a plain section and devices or widgets themselves own the kind, settings etc.", and "do all of them, don't leave anything behind", plus homescreen-style widgets) There is one kind of section, the plain Section, and everything a page shows is a device or a widget inside one. (1) A **widget** is a device of kind `widget` with a type `w`, an id `wid` and the settings of that type in `wx`; the type owns what it is called, its icon, the sizes it can take, how its settings are checked (`clean`), how it is drawn (`draw`, or `section` for an overview that is built as a section of its own) and how its settings are edited (`settings`, `edit`). The types live in one registry (`app/widgetkinds.js`, and `app/homewidgets.js` for the home screen widgets); the registry is also the place a plus integration can add its own through the plugin API later. (2) The old section types became widgets with the same behaviour and the settings they had: Note, Chart, Cameras, Security, Energy, Attention, On now, At a glance, Pinned, Rooms, Linked section, Status tiles (since D-27 a Section, not a widget) and Climate overview. Readings is a size on a device (a sensor as a tile) and Camera is a size on a device (a camera shown live). The lights master, which a Section held (`master`, `masters`, and their tabs, sources and folders), is the widget `lmaster` of the Section: the Section's own (made from its lights) has the Section's id as its id, so its key "page~section" is unchanged, and every other master keeps the id it had; it is a row of the Section, not a tile. A Section that holds only an overview widget is drawn as that widget's own section, so a page looks as it always did. (3) **Sizes** (as on Android and iOS): a section is a grid of four columns; a device or widget has a size `xs` (1 column), `s` (2), `m` (4) or `l` (4, taller). A device that is not a widget is a row of four columns, as before, and the Section's "columns" option still applies to a Section of rows only. Each widget type declares the sizes it supports; a sensor can be `xs` or `s`, a camera `l`. (4) **Layout 7** is the migration: when a dashboard opens, its saved layout is rewritten in memory so that no section has a type other than the plain one, and the new form is saved on the first change, as Layouts 5 and 6 were. Nothing is lost (every setting a section type had is kept on its widget); a section type that was invalid stays dropped. An older Home Control cannot read Layout 7 (it does not know widgets and would drop them), so going back to an older release needs the saved dashboard from before (the backup taken before deploying, or History). (5) The new home screen widgets are Clock and weather, Now playing, Camera snapshot, Vacuum, Power ring, Sensor sparkline, Agenda, To-do, Folder and Stack; each is made of the dashboard's own parts (a tile is a `.gb` tile, a list is rows under a heading, a camera a `.vidbox`, a button a round button), checks the entity it shows is of the right kind, changes something only through a control of its own (the to-do list adds, checks, puts back and removes items; the agenda adds events; a note is written where it is by an administrator), and Stack holds at most five of them (never a stack, an overview or a lights master). Assistant's choices within it: one new device kind `widget` rather than one per type (keeps the list of kinds short and the registry the single place that knows a type); widgets without an entity have an empty `id`; a page may hold any number of each type; Now playing and Vacuum are full-width only (they are rows of an image or icon, text and a button); the vacuum widget has no map (the vacuum's own popup has it); events can be added to a calendar but not removed (Home Assistant has no service for it); Sensor sparkline offers 6 hours, 24 hours and 7 days only (a month of raw points is too much for a small curve).
- D-26 (owner, 2026-11-25: "i have created a new zone in hue app ... there needs to be a way to filter scenes on lights master by hue zone and room ... something like Hue . Zone. Bora's bedroom") The scenes of a lights master, and of a collection of scenes, can be filtered by the room or the zone a plugin's scenes are in. (1) The plugin's scene entities say it in their attributes `group_type` (`room` or `zone`) and `group_name` (documented in `docs/plugin-api.md`); the dashboard reads nothing else and names no brand's attribute elsewhere. (2) The Tags dropdown of the scene sources offers one option for each group found, named *Hue · Room · Bathroom* or *Hue · Zone · Wardrobe* with its number of scenes, rooms before zones; ticking one takes in the scenes of that group. It is kept as a source token `group:<room|zone>:<the name as lower case words joined by hyphens>` next to the others (`page:`, `area:`, `hue:`, `tag:`), so a room and a zone of one name are two groups and renaming a group on the bridge makes its token a different one. (3) Why: the scenes of a Hue room and of the zones in it are all in the same area of Home Assistant (their device's), so the *Hue* choice, which takes in the scenes of an area, brings them together and shows the same scene twice; a group tells them apart. (4) Assistant's choices within it: with rooms ticked only the groups that have scenes in them are offered (all of them when none is, and a group already ticked always); ticking a group stops *Hue* as a whole from taking in everything (it would filter nothing), and unticking the last group does not bring it back; the word *Hue* is the one the dashboard already uses for the plugin; a group only adds scenes (leaving a group's scenes out is not offered). (5) The same two scenes are told apart where they are listed: the Siri and HomeKit page has a heading for each room and zone and names the group in each row's line; the lights master's scenes and a collection add a short word to the name of a scene that has a namesake in another group (" · Zone", or " · Room", with the group's name when two are of one kind). The Home app shows the name Home Assistant gives the scene, so two scenes of one name put on the HomeKit Bridge are two of one name there too.
- D-27 (owner, 2026-11-25: "status tiles per room can be added to the header from header settings in the page editor and the status section is independent and status tiles can be added like adding a standard device") Status tiles live in two independent places, and one setting no longer chooses between them. (1) The **header's status row** of a page is that page's own list of tiles (`UI.stat[page]`), edited in the header's settings (*Status tiles in the header*, for the page picked there) and shown whenever the list is not empty; a tile can show two readings (`h`, a second entity, shown as "a · b"). (2) The **Status Section** is a plain Section whose tiles are sensor devices of size `s`, added like any device (*Add device*, Sensors, with Size). There is no Status widget and no `hdrStatus` setting. (3) **Layout 8** converts what a dashboard showed: with the old setting off, a page's tiles become the Section's devices and its header list is empty; with it on, they stay in the header, the Section is empty, and the Home page's Climate overview tiles become the header's tiles of Home (the overview is hidden, as it was). Nothing a page showed is lost or shown twice. Assistant's choices: the header tile list is per page, not per room only; the Rooms overview takes a room's temperature from the header tile or the Section's temperature sensor.
- D-28 (owner, 2026-11-25: "in section settings, i should be able to select width ... a section 2 or 3 column wide which shrinks down to 1 on mobile automatically") Every Section has an optional width `span` (1 to 4 columns; absent is automatic). The layout never gives a Section more columns than the page has on the screen at hand, so a wider Section shrinks with the screen and is one column on a phone. A Section is placed on the run of columns where the tallest of them is lowest (ties as before), and the rest of the page flows around it. A Section with no width keeps the old rules (full width when it holds a wide widget, or alone between full-width ones); one the person set to one column stays one column. The settings offer Automatic up to the page's number of columns (the last is full width).
- D-29 (owner, 2026-11-25: "Attention should be a device too ... can be added to the header both on the global part and room specific part ... if the attention device has something it will show, if not it hides itself and empty sections should be hidden") Attention is a device (the widget `alerts`), no longer an overview built as a section of its own. (1) In a plain Section it draws the alerts as rows; with nothing to report it draws nothing and the Section holding it is hidden (a Section with no visible device is never shown); while a page is edited it stays, saying there are no alerts, so it can be found and changed. Its settings (which alerts) are unchanged. (2) In the header it is a chip of the global row (`meta.hdr`, kind `alerts`) and a tile of a page's own row (`UI.stat[page]`, `{k:"alerts"}`, one per page); each shows the one thing that needs attention, or how many, and is left out while there is nothing, and a row of only Attention is not shown. (3) It is not kept in a Stack. Existing dashboards need no conversion: their Attention Section becomes a plain Section holding the device. The header's sky is drawn at one stage height (at least 320 px, taller only if the header is), anchored at the top, and the header shows as much of it as it is tall; a header that opens or shuts reveals or clips sky and never stretches or remakes it.
